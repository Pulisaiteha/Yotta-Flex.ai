YottaFlex Data Pipeline: step-by-step demo

An online store has two source systems: a CRM that exports customers as CSV and an order system that exports orders as JSON. The pipeline checks both files, loads the good rows into a reporting warehouse, quarantines the bad rows with a reason, and reports revenue. Work through the steps from top to bottom. Also see Swagger API docs.

How data moves

Steps 1–2: you create customers.csv + orders.json→ Step 3: pipeline reads → validates → transforms → loads→ good rows → warehouse (dim_customer, dim_date, fact_order)+ bad rows → rejected_records→ Steps 4–6: monitoring + reports

Step 0Start clean

Empty everything, then either load the ready-made sample or type your own data in Steps 1–2.

Behind the scenes POST /demo/reset → main.reset_demo() → source_files.clear() + database.clear_all_tables()
POST /source/load-sample → main.load_sample() → source_files.load_sample() copies data/input/* to data/workspace/

Step 1Customer data → customers.csv

This plays the role of the CRM system. Each save writes one row to a real CSV file. Saving an existing ID with a new city replaces that row, which simulates a customer moving (see Step 7).

Behind the scenes POST /source/customers → main.add_source_customer() → source_files.save_customer() writes the CSV.
No validation happens here on purpose: the pipeline validates in Step 3.

Step 3Run the pipeline

    
Reads the two files from Steps 1–2 and loads them into the warehouse in one transaction.

    
    
Behind the scenes
      POST /pipeline/runs with body {...}

      → main.create_run() → main.execute_run() → runner.run_pipeline(), which does:
      
    
        
  1. database.connect() + initialize(): open SQLite and create the tables if missing
    2. 
        
  2. readers.read_customers() / read_orders(): read the files; validation.check_customer_header() fails the run if a column is missing
    3. 
        
  3. validation.validate_customer() + transform.clean_customer() for each customer
    4. 
        
  4. database.upsert_customer(): insert or update dim_customer, logging changes to customer_change_log
    5. 
        
  5. For each order: duplicate check → validation.validate_order() → transform.clean_order() (₹ → paise) → skip if already loaded → database.ensure_date() → INSERT fact_order. Bad rows: runner.record_rejection()
    6. 
        
  6. Write the customer rejections
    7. 
        
  7. metrics.summarize_counts(): check input = accepted + rejected + skipped; write pipeline_runs; COMMIT
    8. 
      

      If anything raises, the transaction rolls back and runner.record_failed_run() stores a FAILED run.

Step 7Things to try

    
    
      
  1. Rerun (idempotency): click Run pipeline again without changing anything.
          Expect accepted 0 and skipped = the earlier accepted count. Revenue in Step 5 does not double.
    2. 
      
  2. Add a new order and rerun: only the new order is accepted; the rest are skipped.
    3. 
      
  3. Customer moves city: in Step 1, save C101 / Ravi / Pune, run the pipeline, then look up C101 in Step 6.
          You'll see the current city plus a history row Hyderabad → Pune.
    4. 
      
  4. Late-arriving order: add a valid order dated earlier than the loaded ones (e.g. 2026-09-01) and run.
          The run reports late_arriving_orders: 1.

  5. Failed run: in Swagger, POST
          /pipeline/runs with a file path that doesn't exist. You get a 404 with a run_id, and Step 4's run history shows a FAILED row.
